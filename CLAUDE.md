# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**arkivet2fs** is a Chrome/Brave browser extension (Manifest V3) that extracts genealogical record data from Norway's DigitalArkivet (digitalarkivet.no) and auto-fills the FamilySearch.org SourceBox "Create Source" form.

### Workflow

1. User navigates to a person/record detail page on DigitalArkivet
2. Clicks the extension icon in the toolbar
3. `background.js` injects `da_record.js` into the DA page and runs its `gatherData()` to extract record metadata, all persons with roles, source info, and builds a citation
4. Extension opens a background tab to FamilySearch SourceBox
5. `content.js` is injected into the FS tab, waits for the "Create Source" button, clicks it, then fills the form fields

## Architecture

- **manifest.json** — Manifest V3 config. No popup; the extension icon click triggers `chrome.action.onClicked` directly. Icons in `icons/` directory.
- **background.js** — Service worker:
  - **Click handler**: Validates DA URL, injects `da_record.js` (`files`), then runs `gatherData()` (`func`; both run in the extension's isolated world of the page, so the second sees the first's functions), checks for errors, opens FS tab, injects `content.js`, sends data.
  - **`fillFormError` listener**: shows a notification for problems reported by `content.js`.
  - **`showErrorMessage()`**: Chrome notification-based error display.
- **da_record.js** — reading a DA record page, used by background.js (injected into the DA page) and by search.html (da_verify.js, on fetched record pages). It uses no other file and declares only functions at the top level, since it's injected again on every click and a second top-level `const` would throw. `extractRecord(document, pageUrl)` does all the extraction (the parameter shadows the global `document`; `pageUrl` stands in for `location`, so it works on `DOMParser` documents) and returns the citation, notes, title, people, and `fields` (the open person's own fields, labels lowercased: `destination`, `marital status`, `migrating to`, ...). `gatherData()` runs it on the open page. If the open page belongs to someone other than the record's principal (e.g. the father on a baptism), `gatherData()` fetches the principal's own page (`/en/<permanent ID>`), parses it with `DOMParser`, and extracts from that instead, so citation, notes, title and link all describe the principal. If that fails, it falls back to the open page. Use `textContent`, not `innerText`, because fetched documents aren't rendered. Helpers inside `extractRecord()`: belongs to someone other than the record's principal (e.g. the father on a baptism), `gatherData()` fetches the principal's own page (`/en/<permanent ID>`), parses it with `DOMParser`, and extracts from that instead, so citation, notes, title and link all describe the principal. If that fails, it falls back to the open page. Use `textContent`, not `innerText`, because fetched documents aren't rendered. Helpers:
    - `validatePermanentId()` — validates 2-alpha + 14-digit format
    - `parseRecordType()` — maps ID prefix to record type (`pd`→birth, `pv`→marriage, `pk`→confirmation, `pg`→death, `pa`→probate, `pf`→census, `pe`→emigration, `pu`→out-migration, `pi`→in-migration, etc.)
    - `formatDate()` — handles full, partial, and missing dates
    - `translateRole()` — Norwegian→English role translation (barn→Child, konfirmant→Confirmand, far→Father, utflyttar→Out-migrant, etc.)
    - `readFields()` / `fieldMap()` — read DA's `<div>Label:</div><div class="ssp-semibold">Value</div>` pairs from the DOM (all field parsing goes through these)
    - `FIELD_CODES` / `translateCensusPosition()` / `translateFieldValue()` — English for coded values, per field: census family position, marital and residential status (HISTFORM codes from DA's key, https://www.digitalarkivet.no/en/content/abbreviations-census; e.g. hp→Head of Household, tj→Servant, fl/l→Lodger, b→Visitor), gender, legitimacy (e/u), roles, and ages ("57 a", "27 A."→"57 years", "27 years")
    - `expandAbbreviations(text, more)` — adds English after abbreviations (`ABBREVIATIONS`, case as written) and whole occupation/position words (`OCCUPATIONS`, any case, old and new spellings) in church-book positions and census occupations, keeping the transcribed text: "Gmd."→"Gmd. [farmer]", "Hj. Søn"→"Hj. Søn [son living at home]", "Murer"→"Murer [mason]", "Pladsfolk under X"→"Pladsfolk [crofters] under X". Census family positions written out instead of coded (1801: "Hosbonde", "Hans kone") also get `RELATIVES` ("Hans kone [wife]"), which occupations don't, since they use family words in passing
    - `extractChurchPeople()` — extracts persons from `#collapse-section-0` `.data-item`s (birth/marriage/death/probate records); the open person (`.data-item.current`) is always included and marked primary
    - `extractCensusPeople()` — extracts residents from `#collapse-persons` `.data-item`s (census records); this lists everyone at the residence
    - `censusHousehold()` — narrows the residents to the open person's household. A residence can hold several (a family, lodgers, ...); each starts at a resident with "H.no." set (not always the "hp"), or at each "hp" when none has an H.no. In the 1801 census every resident has an H.no. (01, 01, 02, ...), so there a household starts where the number changes (lodger households elsewhere each have "1", so this rule is used only when all residents have one)
    - `extractSourceInfo()` — extracts parish, county, source title from page title and detail sections
    - `extractScans()` — scanned-image link(s) from the `#scannedImageLink` toolbar button (`data-scans` holds image permanent IDs: `kb` church book, `ft` census); empty when the record has no scan
    - `buildCitation()` — Evidence Explained–style citation (see `citation.md`): place general→specific (Norway, county, parish/district/municipality from the source title, church), quoted source title, record section, census district/residence/household, protocol/page/line/entry (an emigrant protocol's page and line come from `#collapse-more-info`, read only for emigration since probate pages have it too), entry description (`describeEntry()`), date; then "database, National Archives of Norway, Digitalarkivet, Permanent ID <id> (<permanent link> : accessed <today>)" and "scanned image <id> (<link>)"
    - `recordPrincipal()` — who a record is about, whichever person's page is open: the child (baptism), couple (marriage; the groom's page is used), deceased (burial), confirmand (confirmation), head (first person) of the census household, the emigrant or mover (emigration and moving records; an emigrant protocol lists the travel group, who aren't family, so only the open person counts; a moving record's role is in the person's own fields, "Role: utflyttar"); used by `describeEntry()`, the title, and the switch to the principal's page
    - FS title is "<year>, <principal> - <source title> - <record type>"; a baptized child without a known surname gets ", child of <father/mother>" ("son"/"daughter" when the child's own page gives the gender), since surnames aren't guessed, and a census gets "<head> household" (Birth, Marriage, Burial, ...), FamilySearch's year-first style; "Church book from" / "<year> census for" are dropped from the source title, DA name variants (`%...%`) are stripped from the name, and the type is omitted when the source title already names it (probate)
    - `buildNotes()` — permanent ID, the open person's own fields (split dates like "Date of death: 04-12" + "Year of death: 1854" are merged; full dates like "1812-10-11" become "11 October 1812"), record details not in the citation (banns, remarks, ...), and all persons with their roles
- **fs_person.js** — Phase 1 (see `plan.md`), declared in the manifest for all of `www.familysearch.org` because FS is a single-page app. On a person details page (`/tree/person/details/<PID>`) a `MutationObserver` keeps a "Digital Arkivet" entry (`data-testid=search-digitalarkivet`, icon `icons/da32.png`, a web-accessible resource) after Google's in the Search Records panel. The entry is a `cloneNode` of Google's `li`, which keeps FS styling but none of React's handlers. Clicking it runs `gatherPerson()`, which reads FS's `data-testid`s (`conclusionDisplay:NAME|ALTERNATE_NAME|GENDER|BIRTH|CHRISTENING|DEATH|BURIAL|RESIDENCE`; family cards: own families where the person is in `couple-persons`, otherwise the parents), and sends `{action: 'searchDA', person}` to `background.js`. Reloading the extension cuts off the copy running in open FS tabs (`chrome.runtime.id` is gone and `getURL()` throws "Extension context invalidated"), so `extensionAlive()` is checked first and `shutDown()` stops the observer and removes that copy's own entry (`ownItem`); reloading the FS page brings it back.
- **background.js `personToQuery()`** — turns that person into search criteria in the address of `search.html`, named like FS's record search (`q.givenName`, `q.surname.1`, `q.birthLikeDate.from/to` ±2 years, `q.marriageLike…`, `q.residence…`, `q.deathLike…`, `q.father…`, `q.mother…`, `q.spouse…`, `q.child…`, `q.farm`, `treeref`), and opens the page next to the FS tab. `splitName()` follows the patronymic convention: the given names run up to the patronymic (-sen/-søn/-son, -datter/-dotter, -dtr., -sd.), the patronymic is the surname, and words after it (`rest`) are checked with `farmNear()`; with no patronymic, the last word is the surname. `personToQuery()` is async: the message handler waits for it before opening the tab.
- **farms.js** — loaded with da_places.js by `importScripts` at the top of background.js. `farmNear(name, places, anywhere)` tells a farm from a family or place-derived name (Lindeman): a farm of that name must lie in a municipality or county of the person's FS places (any farm with `anywhere` and no places). It asks Rygh's *Norske Gaardnavne* (`dokpro.uio.no`, UTF-8 `GNAVN`, an HTML table of farm, parish, historical municipality and amt; `parseRygh()`, `amtCodes()` with `PLACE_ALIASES`), then Kartverket's place names (`ws.geonorge.no/stedsnavn`, Gard/Bruk, modern counties via `MODERN_COUNTIES`), with a 5 s timeout each and a cache by name, and also tries the name without Nedre/Øvre/Søndre/... A confirmed farm becomes `q.farm`; otherwise the rest is the surname and the patronymic another name. A last name without a patronymic is also a farm when one lies in the person's places. Uses a local `foldFarm()`, since a `const` of da_places.js isn't visible to the Node tests that `eval` the files separately.
- **search.html / search.js / search.css** — Phase 2 search page (an extension page; no inline scripts). The address is the only store of criteria: the FS-style sidebar (`GROUPS`, on the right with results on the left, as on FS) is filled from it, and Search writes the edited criteria back with `pushState`, so Back/Forward work. Relatives have a use checkbox (`q.fatherSkip=1`, `q.childSkip.1=1`; `profile()` ignores them), "Where to search" adds DA counties/municipalities as chips (`m=`, `c=`; every query gets them as `m[]`/`c[]`, which DA ORs, instead of the automatic narrowing; FS places' municipalities are suggested, never pre-selected), and "Record kinds" (`KINDS`, `off=`) turns queries off by `query.kind` (the id up to `-`). Checkboxes and chips submit at once (`requestSubmit`); unchanged searches come from the page cache. `hintFor()` tells what to change when a search finds too many hits or none. search.js reads the place tables only through da_places.js functions (`municipalityCodeList()`, `countyName()`, ...), since the jsdom tests can't see another file's `const`s. Results: `renderResults()` lists the searches (each with its hit count and an "Open on DA" link to the same search), runs them one at a time (a newer search cancels an older one), and after each one re-renders the merged, scored hits by group; hits scoring below 0 are dimmed. Each group shows `PAGE_SIZE` (10) hits, with a pager below when it has more (`groupSection()`); the page of each group is kept in `groupPages` while hits come in and are re-ranked, and cleared by a new search. Then `checkHits()` reads the record pages of the best hits (da_verify.js; at most `MAX_CHECKS` = 30, each time the best unchecked one, re-rendering after each), stores the reasons on the hit as `checks` (or `checkError`), and says so under the hit ("record checked", "record not read: …") and in `.check-status`; it stops when DA refuses requests and is skipped when a search was refused. Scripts load in this order: da_places.js, da_search.js, da_match.js, da_record.js, da_verify.js, search.js.
- **da_places.js** — DA's counties (`DA_COUNTIES`, `c[]`) and historical municipalities (`DA_MUNICIPALITIES`, `m[]`; a code starts with its county's, Oslo 03 and Bergen 13 are their own), generated from DA's advanced-search form (November 2026); `PLACE_ALIASES` (old and new names: Oslo = Christiania/Chra., Vest-Agder = Lister og Mandal, town abbreviations such as Fr.stad/Fstad, Fr.hald, Chr.sand, Chr.sund, ...); `municipalityCodes(place)` turns an FS place into the municipality codes its parts name (aliases included; a name several counties share is narrowed by the FS county; Oslo adds Aker via `MUNICIPALITY_NEIGHBOURS`). Loaded first. Helpers shared between these scripts are `function` declarations, not `const`s, so the jsdom tests (which `eval` each file) see them.
- **da_search.js** — DA advanced-search queries (`/en/search/persons/advanced`), loaded by search.html after da_places.js, before da_match.js and search.js. `profile(criteria)` turns the sidebar's criteria into one person (year ranges, spouses, children, places, farms). `buildQueries()` gives one query per life event: own baptism by parent (first given name, `roles[]=barn`, a parent as related person; skipped with a hint when no parent is known), own baptism by birthplace (up to two given-name stems, all must match, and `m[]` from the FS birthplace; DA's transcriptions of parents can be far off: Anna Lindeman's Johannes and Gjertrud are "Johanne Olsen" and "Johanne Stubbe"), confirmation, marriage (one per spouse, spouse's first name as related person), children's baptisms (the person as `far`/`mor`), census (`jt[]` census years in the lifetime, `birth_year` ±3), emigration (`sc[]=em`: emigrant protocols, passenger lists, passports; from birth, `birth_year` ±3), moving away (church books' moving lists, `lt[]=uf`/`fl`, records `pu`/`pi`; no `birth_year`, since many give no age), burial (skipped when FS has the death outside Norway), and all records under the name. Each query carries `reasons` its hits all match ("father Aslak"). Name rules learnt from DA: each word of `firstname` must match one of the given names, so the other queries use the first given name only; a trailing `*` works (DA still applies its variants to the stem: Christ* finds Kristian), a `*` inside a word or `?` doesn't. `givenStem()` cuts a final vowel (Anna → Ann*, finding Anne; Magdaline → Magdalin*; Jon, Ole, Johannes stay as they are), `surnameStem()` gives Aslaksen → Aslaks*, Tollefsdatter → Tollefs*, Lindeman → Lindem*; `patronymicOf()` derives the patronymic from the father (Aslak → Aslaksen, Johannes → Johannesdatter, Ole → Olsen), used as the surname when FS has none and for scoring; parents' patronymics aren't used as `related_last_name`. A search with no hits is retried with up to three other names (`variants`: the father's patronymic, FS alternate names, `PATRONYMIC_SPELLINGS` such as Johans*/Johannes*), using only one that finds 100 hits or fewer after narrowing (more are mostly other people; the status says "too many to use as …"); one with over 100 hits is narrowed to the municipalities of the FS places (`narrow`, kept only when hits remain). Farms (`q.farm`) get a "Records at <farm>" query (`domicile`). Never filter on `genders[]`: DA drops records without a gender (many censuses). `parseResults()` reads `#searchResultList .unit`s with `DOMParser`; `fetchResultPage(url, store = true)` spaces requests 1 s apart, caches pages in `sessionStorage` (not with `store` false: da_verify.js keeps only the extract of a record page), and reports 403/429 as DA refusing requests; `runQuery()` applies the retries and narrowing, reads up to 2 pages of 50, and returns `{total, hits, params, notes}`: `params` is the search actually used (the "Open on DA" link), `notes` what was changed (shown in the status).
- **da_match.js** — `mergeHits()` keeps each record once (by permanent ID) with every query that found it; `scoreHit()` scores it against the profile with visible reasons (✓ match, ≈ close or a DA name variant, ✗ contradiction): given names (`nameMatch()`: the same, the stem, or the same consonants via `skeleton()`, so Anne ≈ Anna, Magdalen = Magdaline, John = Joen = Jon, and an old final j after a consonant is i: Sirj = Siri = Siry) and surname stem, sex (only a mismatch counts), birth year (+4 for FS's own year, the middle of the ±2 range), event year by role (baptised/married/buried), before birth or after death, too young for the role (`MIN_AGE`, which flags namesakes), a known child's birth year, FS place parts or their old names (`PLACE_ALIASES`) in the hit, farms (also spelled with the same consonants: Hægbostad = Hægebostad), the query's own reasons, and what the record page said (`hit.checks`, from da_verify.js). `hasWord()` is a function declaration because da_verify.js uses it. On baptisms and confirmations, which give all given names, each one FS doesn't have is -1. `groupHits()` groups by record kind and role (`GROUP_ORDER`; out- and in-migration go to Moving; a father's row in a baptism goes to Children's baptisms, a godparent's to Other), best first.
- **da_verify.js** — checks close hits on their record pages, since a hit gives only one person's name, years and residence (three Peer Aslaksens in the 1801 census score alike). `hitsToCheck()` takes the best few of each group (`CHECK_PER_GROUP`, 8 children's baptisms, otherwise `CHECK_DEFAULT` 3; score ≥ `CHECK_MIN_SCORE`; groups in `CHECKED_GROUPS`). `fetchRecord()` reads the page with `extractRecord()` and keeps `{people, fields, recordTypeInfo, recordDate}` in `sessionStorage` (`rec:<url>`). `relativesInRecord()` finds who'd be the person's father, mother, spouse and children by both roles (`roleKind()`, `ROLE_KINDS`: DA roles and census positions, including 1801's free text such as "Hosbonde", "Hans kone", "Deres børn"; only the first of "d, fl" counts); in a census household the head and the head's spouse are both a child's parent candidates. `checkRecord(record, profile)` gives reasons like `scoreHit()`'s: an FS parent or spouse named in the record ✓ +3, another name there ✗ -2 (not for census parents: foster and step-parents), FS children ✓ +2 each (at most three, birth year ±2, from an age in a census), unmarried in a census after FS's marriage ✗ -3, an emigrant's destination among the FS places ✓ +2 ("going to Denver Col."). DA's transcriptions of names can be far off, hence the small minus.
- **content.js** — Content script injected into FamilySearch. Listens for `fillForm` message, checks it landed on the SourceBox (not a sign-in redirect), clicks the "Create Source" button, waits for form elements (with 10s timeout), and fills them using `dispatchEvent` to trigger React's synthetic event handling. Failures are sent back to `background.js` as `fillFormError`.

### Key Constraints

- `da_record.js` executes in the DA page context (injected via `chrome.scripting.executeScript`) and in search.html. **It must not use anything from other files**, and declares only functions at the top level (it's injected again on every click).
- Form filling in `content.js` requires dispatching `input`, `change`, and `blur` events for FamilySearch's React-based UI to register the values.
- DA Permanent IDs: two alpha characters + 14+ numeric digits (e.g., `pd00000012345678`). The prefix indicates record type (see `ai_prompt.md` for the full table).

### DA Page Structure Differences

- **Church records** (birth `pd`, confirmation `pk`, marriage `pv`, death `pg`): URL `/view/NNN/pXXX`, persons in `#collapse-section-0`, record details in `#collapse-section-1`, header in `div.parent-post > h4`
- **Census records** (`pf`): URL `/census/person/pfXXX`, persons in `#collapse-persons`, details in `#collapse-more`, no parent-post header

## Development

This is a browser extension with no build step, no package manager, and no test framework. To develop and test:

- Load as unpacked extension in Chrome/Brave via `chrome://extensions` → "Load unpacked" → select repo directory
- After code changes, click the reload button on the extension card in `chrome://extensions`
- Debug with the browser DevTools: service worker console (click "Inspect views: service worker" on the extension card) and page console for content script logs

## Host Permissions

The extension requires access to `https://*.familysearch.org/*` and `https://*.digitalarkivet.no/*`, and for the farm check (farms.js) `https://www.dokpro.uio.no/*` (Rygh) and `https://ws.geonorge.no/*` (Kartverket).
