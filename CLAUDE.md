# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**arkivet2fs** is a Chrome/Brave/Firefox browser extension (Manifest V3, one package for Chromium and Firefox 140+) that extracts genealogical record data from Norway's DigitalArkivet (digitalarkivet.no), turns it into a FamilySearch.org source, and attaches the source to the tree persons the record names.

### Workflow

1. On an FS person page, the "Digital Arkivet" entry (fs_person.js) opens the search page (search.html), which searches DA and ranks the hits
2. "Review & Attach" on a hit, or the extension icon on a DA record page (`background.js` injects `da_record.js` and runs its `gatherData()`), opens the linker (linker.html)
3. The user reviews and edits the source and pairs the record's people with tree persons; nothing goes to FS before "Create source and attach" ("Update source and attach" when the SourceBox has the source)
4. The linker drives an FS tab with `fs_attach.js`: create the source in the SourceBox, attach it to each person by PID, add the tags

## Architecture

- **manifest.json** — Manifest V3 config. No popup; the extension icon click triggers `chrome.action.onClicked` directly. `storage` holds the linker's draft records (session), FS persons, the linker's finished runs (`done`) and the update check's state (local); `alarms` is for the daily update check. `background` names both `service_worker` (Chromium, which ignores `scripts`) and `scripts` (Firefox's event page: i18n.js, i18n_strings.js, names.js, da_places.js, farms.js, releases.js, then background.js, the files background.js's `importScripts` loads, which it calls only when it exists; background.test.js checks they agree). `browser_specific_settings.gecko`: `id` `arkivet2fs@dude4linux` (permanent once on AMO), `strict_min_version` 140.0, `data_collection_permissions` `{required: ['websiteContent'], optional: ['technicalAndInteraction', 'personallyIdentifyingInfo']}` (since 1.7.0: the sources are DA's and FS's content, sent to FS; the optional two are asked for when a report is sent, report.js `askToSendReport()`; report.test.js checks them). The update check's GitHub hosts are `optional_host_permissions` (decision 11).
- **icons/** — the "Kirkebok" mark: an open church book with a pedigree (the person in copper, two parents) growing from its spine; sky blue `#4a88c4` (the tile, chosen to stand out on both light and dark toolbars), deep sky `#2e547a` (the ring around the person, at every size, and the ruled lines), parchment `#f4ecdc`, copper `#d0843f`. The README banner (`banner.html`) uses the same colours: the mark on a parchment ground, the name and tagline in deep sky, its "2" in a darker copper `#b0621f` for contrast. `icon128.svg` is the full mark, `icon48.svg` drops the pages' ruled lines, `icon32.svg` has heavier lines (favicon and header of search.html, toolbar at 2x), `icon16.svg` is drawn for 16 px. The PNGs (manifest icons, notifications use `icon128.png`) are rendered from the SVGs with headless Chrome (`--default-background-color=00000000` keeps the corners transparent); `banner.html` → `banner.png` (2x, the README banner; its command is in the file). The FS entry (fs_person.js) shows `icon32.svg` at 24 px, the manifest's only web-accessible resource.
- **background.js** — Service worker:
  - **Click handler**: Validates the DA URL (`isDigitalArkivet()`: https and the host www.digitalarkivet.no, the manifest's (digitalarkivet.no without www. redirects there); without the `tabs` permission a tab the extension may not touch has no `url`), injects `names.js` and `da_record.js` (`files`), then runs `gatherData()` (`func`; all run in the extension's isolated world of the page, so the second sees the first's functions), checks for errors, keeps the result in `chrome.storage.session` (`draft:<time>`) and opens `linker.html?draft=<key>` next to the DA tab.
  - **`rememberPerson()`**: on `searchDA`, keeps the FS person (fs_person.js's `gatherPerson()`, with the family's PIDs) in `chrome.storage.local` as `person:<PID>`, and `persons` (`{pid, name}`, most recent first, at most `MAX_PERSONS` = 30; older `person:` keys are removed), for the linker.
  - **`onInstalled` listener**: injects `fs_person.js` again into open FamilySearch tabs after an install, update or reload (failures, e.g. discarded tabs, are only logged).
  - **`showErrorMessage()`**: notification-based error display (no `buttons`: Firefox has none; cleared after 5 s).
  - **Update check** (release-plan.md, Phase 3; the functions are releases.js's): only when `chrome.management.getSelf()` gives `installType` `development` (unpacked; a store updates its own copy, and nothing runs there, not even the alarm). `startUpdateChecks()` at each worker start creates the daily alarm `update-check` if missing and runs `checkForUpdate()`, which asks GitHub only once `updateHostsGranted()` (releases.js: `permissions.contains()` of `updateOrigins()`, the optional GitHub hosts; without them nothing is asked and `pendingUpdate()` shows nothing; `permissions.onAdded`/`onRemoved` check or redraw) and when `updateDue()` (23 h since `update.checked`) and `updateCheck` isn't false (`force`: update.html's "Check now", message `{action: 'checkUpdate'}`, answered with `{state}`; also on a change of `updateDev`), keeps the answer as `update`, then `showUpdate()`: `pendingUpdate()` (`newerRelease()` with `updateChoice`) gives the badge "↑" (copper `#b0621f`) or none, and one notification per version (`update:<version>`, `update.notified`), which opens update.html. Clicking the icon on a non-DA page with a pending update opens update.html instead of the error. `storage.onChanged` on `updateCheck` checks if due, on `updateChoice` redraws the badge.
- **da_record.js** — reading a DA record page, used by background.js (injected into the DA page) and by search.html (da_verify.js, on fetched record pages). It uses no other file but names.js (injected before it) and declares only functions at the top level, since it's injected again on every click and a second top-level `const` would throw. `extractRecord(document, pageUrl)` does all the extraction (the parameter shadows the global `document`; `pageUrl` stands in for `location`, so it works on `DOMParser` documents) and returns the citation, notes, title, people, `fields` (the open person's own fields, labels lowercased: `destination`, `marital status`, `migrating to`, ...), `sourceTitle`, `sourceUrl` (the infobox's `#source-link`, DA's `/source/NNN` page, only a www.digitalarkivet.no address; the record page doesn't name the book, the source page does), and `county` (from `extractSourceInfo()`; "Akershus, Oslo" for a source of two; none for "Hele Norge", the Danish chancery's registers), and `church` (the Parish/Church detail, often "-": empty). `gatherData()` runs it on the open page; on a Bokmål or Nynorsk page (`englishPageUrl()`) it fetches and reads DA's English page of the same address instead, falling back to the open page. If the open page belongs to someone other than the record's principal (e.g. the father on a baptism; for a marriage, anyone but the groom, the bride too), `gatherData()` fetches the principal's own page (`/en/<permanent ID>`), parses it with `DOMParser`, and extracts from that instead, so citation, notes, title and link all describe the principal. If that fails, it falls back to the open page. Use `textContent`, not `innerText`, because fetched documents aren't rendered. Helpers inside `extractRecord()`:
    - `validatePermanentId()` — validates 2-alpha + 14-digit format
    - `parseRecordType()` — maps ID prefix to record type (`pd`→birth, `pv`→marriage, `pk`→confirmation, `pg`→death, `pa`→probate, `pf`→census, `pe`→emigration, `pu`→out-migration, `pi`→in-migration, etc.)
    - `formatDate()` — handles full, partial, and missing dates (a header date DA wrote wrong, "1803-2702", is cut to its year before it, the record's `recordDate` too; a range of years, "1740-1743" or "1740-43", stays; a header naming the record this one belongs to by its permanent ID, a royal resolution's "Type of letter: oc…", gives the type "Letter" and the date of the record's own Date field)
    - `translateRole()` — Norwegian→English role translation (barn→Child, konfirmant→Confirmand, far→Father, utflyttar→Out-migrant, ektemann→Husband, etc.)
    - `readFields()` / `fieldMap()` — read DA's `<div>Label:</div><div class="ssp-semibold">Value</div>` pairs from the DOM (all field parsing goes through these)
    - `FIELD_CODES` / `translateCensusPosition()` / `translateFieldValue()` — English for coded values, per field: census family position, marital and residential status (HISTFORM codes from DA's key, https://www.digitalarkivet.no/en/content/abbreviations-census; e.g. hp→Head of Household, tj→Servant, fl/l→Lodger, b→Visitor; marital status also as written out: Ugift, Gift, Enke, Enkemand), gender, legitimacy (e/u), roles, and ages ("57 a", "27 A."→"57 years", "27 years")
    - `expandAbbreviations(text, more)` (top-level, with its tables in the top-level `positionWords()`, made once per injection, since search.js `positionText()` uses it too: the search page's Position line in the English UI, a census hit's with the relatives) — adds English after abbreviations (`abbreviations`, case as written) and whole occupation/position words (`occupations`, any case, old and new spellings) in church-book positions and census occupations, keeping the transcribed text: "Gmd."→"Gmd. [farmer]", "Hj. Søn"→"Hj. Søn [son living at home]", "Murer"→"Murer [mason]", "Pladsfolk under X"→"Pladsfolk [crofters] under X". Census family positions written out instead of coded (1801: "Hosbonde", "Hans kone") also get `relatives` ("Hans kone [wife]"; "Barn" a child, "Børn" children; the compounds too: "hans Søstersøn [sister's son]", Brodersøn, Svoger, Svigerinde, Barnebarn, Oldebarn, Bedstefader, Stedmoder, Pleiefader, Halvbroder, Søskendebarn/Fætter/Kusine, Nevø, Niese, Mand [husband], ...), which occupations don't, since they use family words in passing
    - `townInFull()` / `placeWithTown()` (top-level; linker.js `recordFacts()` uses the first) — a clerk's abbreviation of a town, the place alone, in full as the town was named then ("Fhald"/"Fr.hald" → Fredrikshald, "Fstad", "Chr.sand", "Chr.sund", "Chra."/"Kria.", "Thjem" → Trondhjem); the notes keep it as written with the name after it ("Birth place: Fhald [Fredrikshald]", `translateFieldValue()` for place and residence fields, `personLine()`)
    - names.js `abbreviationPoint()` — a colon closing a word of a name, the church books' abbreviation mark ("Larsdat:"), becomes a point ("Larsdat."), for every person's name once the people are read (da_search.js `parseResults()` the same for hit names); "d:r" inside a word stays
    - `extractChurchPeople()` — extracts persons from `#collapse-section-0` `.data-item`s (birth/marriage/death/probate records); the open person (`.data-item.current`) is always included and marked primary. An emigrant protocol's section lists the whole protocol 50 at a time ("Load more"), so the open person is often not among them; `extractRecord()` then adds them from their own fields (first name, surname, role, occupation, year of birth, residence)
    - `extractCensusPeople()` — extracts residents from `#collapse-persons` `.data-item`s (census records); this lists everyone at the residence, 50 at a time: `loadMoreResidents(doc, fetchText)` (async, run before `extractRecord()` by `gatherData()` on a copy of the open page and on the principal's page, by linker.js `loadFromDA()` and da_verify.js `fetchRecord()`) follows the `.load-more` `data-url` (JSON `{view, nextPage}`, at most 20 pages, only DA addresses: `onDigitalArkivet()`; `view` parsed by `DOMParser` inside a `<template>`, inert, no `innerHTML`, which AMO's linter flags) and adds the rest, cards before the `.load-more`, table rows into the table, so a resident past the 50th (1801 Nordby has 74) and their household are found; an emigrant protocol's "Load more" (the whole protocol) isn't followed. Without the open person among the people, no principal page is used. DA shows them as cards (`h4 a`, label/value fields; fetched pages) or, with the table view the user's browser has, as `tr.data-item` rows: `rowFields()` maps the cells by the `th` headings, taken from floatThead's floating copy of the table when the table's own `th`s are empty (the open page)
    - `censusHouseholds()` / `censusHousehold()` — split the residents into households and pick the open person's. A residence can hold several (a family, lodgers, the old parents on føderaad, ...); each starts at a resident with "H.no." set (not always the "hp"; "000" is none: 1891 gives the head "1" and the rest "000"), or at each "hp" when none has an H.no. In the 1801 and 1865 censuses every resident has an H.no. (01, 01, 02, ...), so there a household starts where the number changes (lodger households elsewhere each have "1", so this rule is used only when all residents have one). A household's first resident with no family position (1865) is its "Head of Household". The other households are returned as `others` and listed in the notes under "Also at the residence, household no. NN"
    - `extractSourceInfo()` — extracts parish, county, source title from page title and detail sections
    - `extractScans()` — scanned-image link(s) from the `#scannedImageLink` toolbar button (`data-scans` holds image permanent IDs: `kb` church book, `ft` census); empty when the record has no scan
    - `buildCitation()` — Evidence Explained–style citation (see `citation.md`): place general→specific (Norway, county, parish/district/municipality from the source title, church), quoted source title, record section, census district/residence/household, protocol/page/line/entry (`citePage()`: "p. 24", two pages "pp. 260–261" (DA's "260, 261"; consecutive or with a dash) or "pp. 12 and 15"; an emigrant protocol's page and line come from `#collapse-more-info`, read only for emigration since probate pages have it too), entry description (`describeEntry()`), date; then "; database, National Archives of Norway, Digitalarkivet;" and, each on a line of its own, "Permanent ID: <id> (<permanent link> : accessed <today>);" and "Scanned image: <id> (<link>)" (fs_attach.js `recordIds()` reads the ID with or without the colon, as sources made before have it)
    - `recordPrincipal()` — who a record is about, whichever person's page is open: the child (baptism), couple (marriage; the groom's page is used), deceased (burial), confirmand (confirmation), head (first person) of the census household, the emigrant or mover (emigration and moving records; an emigrant protocol lists the travel group, who aren't family, so only the open person counts; a moving record's role is in the person's own fields, "Role: utflyttar"); used by `describeEntry()`, the title, and the switch to the principal's page
    - FS title is "<principal> - <source title> - <record type>, <record date>", as FS titles its own records' sources (no year in front since 1.6.0: the SourceBox shows the source date's year in front of the title and sorts by it; the date at the end, "- Birth, 23 August 1846", keeps two records of one name, parents and parish apart, a child named after a brother who died; not for a census, whose title ends with its year; linker.js `formerTitles()` gives the older titles: year-first, also a census's as edited by hand, and without the date at the end (1.6.0's first builds; the date a full one, a month, a year or a range of years), which `lookUpSource()` also looks for: fs_attach.js `findSource` with `older` and `search` (the dateless title, which all of them hold: one search) matches them among the same search's rows, a census's is searched for itself; a source found by a former title is read first (`readSourceFields()`, with the source and `sameRecordIds()`) and only this record's are kept, else none is found and a new one is made; the update gives it the new title, `editSource` finding the row by `title`); a baptized child without a known surname gets ", child of <father/mother>" ("son"/"daughter" when the child's own page gives the gender), since surnames aren't guessed, and a baptized or buried child without a name in the source ("!! Halvorsd.*": "!!" for the name, the starred patronymic the transcriber's; `unnamedChild()`) is only "son of <father>", its citation's entry "burial of a son of <father>" (linker.js `unnamedChildTitle()` puts the paired tree person's name in its place), and a census gets "<head> household, <residence>, <census district>" ("Halvor Larsen household, Bakken nedre, Nordlien - Vågå - \"Norway, Census, 1865\"", ending as FS's own census sources do, "Norway, Census, 1801", in place of the type; the names from the `div.parent-post > h4` lines "Census district: 005 Nordlien", "Rural residence: 0008 Bakken nedre" without their numbers, none when DA gives only a number such as "001*"; also returned as `census: {district, residence}`) (Birth, Marriage, Burial, ...); "Church book from" / "<year> census for" are dropped from the source title, words the source struck out (DA's `%...%`) are left out of the name and two readings ("Even@Sven") written "Even/Sven" (names.js `stripNameVariants()`, which linker.js uses too), and the type is omitted when the source title already names it (probate)
    - `buildNotes()` — permanent ID, a census's district and residence lines as DA writes them, the open person's own fields (DA's "Last name" holds everything after the first given name; `noteNames()` keeps only its last word as the surname, with a farm-part word such as Nedre/Øvre, and moves the rest to the given name: "Hans" + "Sørensen Lindemann" → "Hans Sørensen" + "Lindemann";split dates like "Date of death: 04-12" + "Year of death: 1854" are merged, and a baptism's date of birth (a burial's date of death) with no year field, "Date of birth: 04-02", gets the record's year, or the year before when the day comes after the record's ("2 April 1821"); a baptism dated before a date of birth with its year gets a "Remark: the baptism, …, is dated before the birth, …" line, since the title and citation keep DA's date; full dates like "1812-10-11" become "11 October 1812"), record details not in the citation (banns, remarks, ...), and all persons with their roles (`personLine()`: a census age as "age 35", a year as "b. 1841", 1910's full date as "b. 6 April 1845", by the top-level `fullBirthDate()`, which also reads "1892-11-14@17", the age after it; linker.js `recordFacts()` takes it as the birth date), then a census residence's other households; DA's special signs get English after them in the person lines ("!!" alone: "!! [no name in the source]"; a word ending in "!!": "[evidently wrong in the source]"; a word with "??": "Ann?? [illegible]"; linker.js `renameNoteLine()` finds the line either way), and the notes end with "--- Signs in DigitalArkivet's transcription ---", one line for each sign used in them (`signsLegend()`: "??", "!!", "*" after a value (`\S\*`, not the notes' own " *" after the open person), "%...%", "@", "E:")
- **fs_person.js** — Phase 1 (see `plan.md`), declared in the manifest for all of `www.familysearch.org` because FS is a single-page app. On a person details page (`/tree/person/details/<PID>`) a `MutationObserver` keeps a "Digital Arkivet" entry (`data-testid=search-digitalarkivet`, icon `icons/icon32.svg`, a web-accessible resource) after Google's in the Search Records panel. The entry is a `cloneNode` of Google's `li`, which keeps FS styling but none of React's handlers. Clicking it runs `gatherPerson()`, which reads FS's `data-testid`s (on FS's English or Norwegian pages: the sex as Male/Female or Mann/Kvinne, normalized by `sexOf()`, Norwegian alternate-name types and event titles) (`conclusionDisplay:NAME|ALTERNATE_NAME|GENDER|BIRTH|CHRISTENING|DEATH|BURIAL|RESIDENCE|OCCUPATION|EMIGRATION|IMMIGRATION`; an occupation's description is its text without the date and place, not yet seen on FS, and `OTHER_EVENT`s whose `conclusion-title` is Emigration or Immigration (custom events: an emigrant can have "Immigration 1866" and "1867" besides the fact 1868); family cards: own families where the person is in `couple-persons`, otherwise the parents), and sends `{action: 'searchDA', person}` to `background.js`. Reloading the extension cuts off the copy running in open FS tabs (`chrome.runtime.id` is gone and `getURL()` throws "Extension context invalidated"), so `extensionAlive()` is checked first and `shutDown()` stops the observer and removes that copy's own entry (`ownItem`). background.js injects the script again into open FS tabs on `chrome.runtime.onInstalled` (install, update, reload; Chrome doesn't inject the manifest's content scripts into open tabs), and a starting copy replaces any entry already there, so the entry comes back without reloading the page. It also answers `{action: 'readPerson'}` (linker.js, on a details page it opened) with `{person: gatherPerson()}` once FS shows the name and family cards (`readWhenShown()`, 20 s), or `{error}`.
- **background.js `personToQuery()`** — turns that person into search criteria in the address of `search.html`, named like FS's record search (`q.givenName`, `q.surname.1`, `q.birthLikeDate.from/to` ±2 years (±1 with a full birth date, `parseFsDate()` exact), `q.birthLikeDate` (FS's birth date as written, else the christening year; the sidebar's Date field), `q.marriageLike…`, `q.residence…`, `q.deathLike…`, `q.emigrationLike…` (the years of the emigrations and of immigrations to places outside Norway, ±2, and the departure place), `q.abroadPlace`/`q.abroadYear` (the first dated residence, marriage, death or burial outside Norway (`placeAbroad()`) no earlier than the last dated event in Norway; a birth abroad doesn't count), `q.father…`, `q.mother…`, `q.spouse…`, `q.child…` (each with `…BirthYear` from the FS lifespan; a relative's surname is the patronymic and the rest after it, "Olsdtr Moen"), `q.farm`, `treeref`), and opens the page next to the FS tab. Names go through `withoutNickname()` first (a quoted word, a leading Big/Little/Stor/Lille/Gamle/...: "Big 'Stor' Lars Halvorsen" → "Lars Halvorsen"), so two brothers Lars don't add "Little" as a given name. `q.birthLikePlace` is the more specific of the birth and christening places ("Vågå, Oppland, Norway", not "Norway"). names.js `splitName()` follows the patronymic convention: the given names run up to the patronymic (-sen/-søn/-son, -datter/-dotter, -dattr., -datt., -dat., -dtr., -sd:r, -sd., -sd), the patronymic is the surname, and words after it (`rest`) are checked with `farmNear()`; with no patronymic, the last word is the surname; a patronymic joined to the farm by a hyphen ("Olsdtr-Moen", "Olsdtr- Moen") is split there. `personToQuery()` is async: the message handler waits for it before opening the tab.
- **farms.js** — loaded with da_places.js by `importScripts` at the top of background.js. `farmNear(name, places, anywhere)` tells a farm from a family or place-derived name (Lindeman): a farm of that name must lie in a municipality or county of the person's FS places (any farm with `anywhere` and no places). It asks Rygh's *Norske Gaardnavne* (`dokpro.uio.no`, UTF-8 `GNAVN`, an HTML table of farm, parish, historical municipality and amt; `parseRygh()`, `amtCodes()` with `PLACE_ALIASES`), then Kartverket's place names (`ws.geonorge.no/stedsnavn`, Gard/Bruk, modern counties via `MODERN_COUNTIES`), with a 5 s timeout each and a cache by name, and also tries the name without Nedre/Øvre/Søndre/... A confirmed farm becomes `q.farm`; otherwise the patronymic stays the surname (searched first: church books name people by it) and the rest is another name (`q.surname.1`). A last name without a patronymic is also a farm when one lies in the person's places. Uses its own `foldFarm()`.
- **search.html / search.js / search.css** — Phase 2 search page (an extension page; no inline scripts). The address is the only store of criteria: the FS-style sidebar (`GROUPS`, on the right with results on the left, as on FS) is filled from it, and Search writes the edited criteria back with `pushState`, so Back/Forward work. Relatives have a use checkbox (`q.fatherSkip=1`, `q.childSkip.1=1`; `profile()` ignores them), "Where to search" adds DA counties/municipalities as chips (`m=`, `c=`; every query gets them as `m[]`/`c[]`, which DA ORs, instead of the automatic narrowing; FS places' municipalities are suggested, never pre-selected), and "Record kinds" (`KINDS`, `off=`) turns queries off by `query.kind` (the id up to `-`). Checkboxes and chips submit at once (`requestSubmit`); unchanged searches come from the page cache. The page copies the look of FS's record search (search.css: Noto Sans 16 px, teal `#057091` buttons and `#005c82` links, FS's grey event boxes in the criteria panel, whose Search button sticks to its bottom under a sticky header); each hit is a row in FS's columns (`hitRow()`: name, role and source link; events, with DA's dates as FS writes them via `displayDate()`, "6 April 1845"; how it matches; score) under column headings (`colHead()`). `hintFor()` tells what is still missing (the query's goal), or what to change when every search found too many hits or none. search.js reads the place tables only through da_places.js functions (`municipalityCodeList()`, `countyName()`, ...). Results: `renderResults()` lists the queries (each with "N hits from K of M searches" and an "Open on DA" link to the first search that was read; `stepList()` lists every search run, its step and place, linked to DA, with its count), runs them one at a time (a newer search cancels an older one), and after each one re-renders the merged, scored hits by group (merged per step, so the step's `reasons` count); hits scoring below 0 are dimmed. A hit of a record the linker has done (`chrome.storage.local` `done`, linker.js `rememberDone()`; `doneIndex()` maps each of an entry's `ids` to the latest entry, `doneFor()` by the hit's or its `parallel`'s ID) gets `doneLine()`: "✓ Attached 10 November 2026 to Lars Halvorsen, Halvor Larsen · 1 fact added or changed" ("⚠ Not all done …" when a step failed, "Added to your SourceBox …" with no one attached), linked to the first source's Attached To page, the row's class `done` (an `--ok` edge) and `mine` (tinted) when `treeref` has the source, and "Review again"; `watchDone()` reads `done` at start and on `storage.onChanged`, and `setDone()` redraws only the shown rows (`rowHits`) whose entry changed. `renderGroups()` scores with `P.anchors` widened by `recordAnchors(merged, treeref)`: the `place` of each `done` entry with the `treeref` person among its sources' persons, and `hitPlace()` of each hit whose `checks` have a ✓ of 3 points or more (an FS parent or spouse named, the FS birth date) and no ✗, each with its `id`. Each group shows `PAGE_SIZE` (10) hits, with a pager below when it has more (`groupSection()`); the page of each group is kept in `groupPages` while hits come in and are re-ranked, and cleared by a new search. Then `checkHits()` reads the record pages of the best hits (da_verify.js; at most `MAX_CHECKS` = 40, each time the best unchecked one, re-rendering after each), stores the reasons on the hit as `checks` (or `checkError`), and says so under the hit ("record checked", "record not read: …") and in `.check-status`; it stops when DA refuses requests or is down and is skipped when a search stopped on that (`daStopped()`); then, and when a search starts while `daPause()` holds (nothing is sent; the queries say "Not run"), `daWarning()` puts the message above the results with "Try again now" (`clearDaPause()`, the same search again). Both pages start through access.js `whenSiteAccess()`. ### Key Constraints

- `da_record.js` executes in the DA page context (injected via `chrome.scripting.executeScript`) and in search.html. **It must not use anything from other files but names.js**, which is injected before it (`files: ['names.js', 'da_record.js']`) and loaded before it on both pages; both declare only functions at the top level (they're injected again on every click).
- Form filling in `fs_attach.js` sets values through the native setter and dispatches `input`, `change`, and `blur` events for FamilySearch's React-based UI to register them.
- FS's `/platform/` API isn't used (it needs a session token); attaching is UI automation of the SourceBox and the Sources tab, started only by the user on the linker page.
- DA Permanent IDs: two alpha characters + 14+ numeric digits (e.g., `pd00000012345678`). The prefix indicates record type (see `ai_prompt.md` for the full table).

### DA Page Structure Differences

- **Church records** (birth `pd`, confirmation `pk`, marriage `pv`, death `pg`): URL `/view/NNN/pXXX`, persons in `#collapse-section-0`, record details in `#collapse-section-1`, header in `div.parent-post > h4`
- **Census records** (`pf`): URL `/census/person/pfXXX`, persons in `#collapse-persons`, details in `#collapse-more`, no parent-post header

## Development

This is a browser extension with no build step. The extension itself has no dependencies; `package.json` is only for the tests and the lint (Node ≥ 22.13, jsdom and web-ext, nothing of it ships). To develop and test:

- **Tests**: `npm install` once, then `npm test` (Node's own `node --test`, about 2 s, offline). `tests/harness.js` loads the extension's files into a jsdom window as the pages do: `load(files, {html, url, lang, chrome, fetch, fast})` runs each file as a classic script (`node:vm`), so functions are the window's properties and a name declared twice across files throws, as in the browser; `loadBackground()` runs background.js with a `chrome` stub and `importScripts`; `fixtureDoc()`/`fixtureUrl()` give a saved page and its address, `unnamedBurial(win)` the burial fixture as an unnamed child's ("!! Halvorsd.*") with a father. The tests (`tests/*.test.js`, one per file of the extension, and `tools.test.js` for `tools/`) use saved DA pages in `tests/fixtures/da/` (record pages and trimmed search result pages; their first line is the address and day) and synthetic FS persons (`TEST-…` PIDs, built in the tests: never save FamilySearch pages, which hold living people and other users' work). `search.test.js` runs the whole search page against a fake DA (`fetch` answered from the fixtures, `fast` timers). `fs_attach.test.js` runs the read-only steps on made-up FS pages built with FS's `data-testid`s, and linker.test.js `fakeFs()` answers `run()`'s steps behind a `chrome.tabs` stub. The fixtures are real DA pages of cases the code must handle, sanitized: `node tests/capture.js <name> <DA address or permanent ID>` saves a page in `tests/private/raw/` (historical records only, one at a time; it strips scripts and the search form), and `node tests/sanitize.js` writes `tests/fixtures/da/` with made-up names (patronymics follow the made-up father), IDs (`pd99…`) and links, checking that `extractRecord()`/`parseResults()` read the same from both but for the swapped names. `tests/private/` (gitignored, never published) holds the raw pages, `names.json` (fixture names, fixed real → made-up names; optional, so a contributor's fresh clone can sanitize a page) and `map.json` (every swap so far; keep it, or the fixtures' names and IDs change). No real family names in the repo: tests use the made-up ones. Write expectations from the documented behaviour, not from what the code gives; a test for each bug fixed. See `tests/README.md`.
- **Repository**: https://github.com/Dude4Linux/arkivet2fs (public, GPL-3.0-or-later) is the main repo; git-server (`ssh://git@git-server/Personal/arkivet2fs.git`, Forgejo, the organization Personal) is a read-only pull mirror of it: push only to GitHub (the remote `origin`; the mirror is `forgejo`). Commits use the GitHub noreply address (`1219334+Dude4Linux@users.noreply.github.com`; `~/.gitconfig` sets it for every repo with a GitHub remote). The history was rewritten once, before going public (`git filter-repo`, November 2026), to take out the real family names, DA and FS IDs and the personal email; every hash changed then. `.github/workflows/ci.yml` runs on each push to master and each pull request: `npm ci`, `node --check` on every script, `sh -n` and shellcheck on the shell scripts, a check that `tests/fixtures/` holds no real DA permanent ID (a made-up one has `99` after the prefix), `npm test`, and a build of the package (`tools/build.mjs`, kept 7 days as the run's artifact); then `web-ext lint` (Mozilla's addons-linter, `web-ext` in package.json) on the unzipped package (warnings shown: the ignored `service_worker`, Firefox for Android; errors fail); its actions are pinned to commit SHAs and its token only reads. `SECURITY.md` says how to report a problem (GitHub's private reporting) and what the extension does with the user's data; `PRIVACY.md` is the privacy policy the store listings link to, as the website's `docs/privacy.html` (https://dude4linux.github.io/arkivet2fs/privacy.html; GitHub answers the Chrome Web Store's fetch of a file page with 503), made from it by `node tools/site-pages.mjs` (which also makes `docs/guide.html` from `docs/guide.md`), which tools.test.js checks (the hosts, what is read on FS, what is kept, the reports; keep it, SECURITY.md's section, `store/review.md` and the stores' data forms in step when that changes); `store/` holds the listings' texts (`listing.md`: names, descriptions in English and Bokmål, categories; `review.md`: the single purpose, each permission's reason, the data-use answers, reviewer notes; `screenshots/`: the four 1280×800 shots, made by `make.sh` (`render.js` sets up search.html or linker.html in the tests' harness on the fixtures and `TEST-` persons, then headless Chrome)), excluded from the package with PRIVACY.md; the README's "Problems and contributing" says how to contribute.
- **The report relay** (`relay/`, since 1.7.0; not in the package): `worker.mjs`, a Cloudflare Worker (`wrangler.toml`: `REPO_OWNER`/`REPO_NAME`, the `LIMITER` rate limit, 3 a minute per `CF-Connecting-IP`; secrets `APP_CLIENT_ID`, `INSTALLATION_ID`, `PRIVATE_KEY`), `relay(request, env, fetch)`: only `POST /report` (OPTIONS answered for CORS) from an extension origin (`allowedOrigin()`: `chrome-extension://` 32 letters a–p or `moz-extension://` a UUID, or `ALLOWED_ORIGINS`), at most `MAX_REQUEST` (200,000) characters, `readReport()` (a report, version X.Y.Z, page lowercase letters, browser and contact made one line), then `fileReport()`: an installation token (`installationToken()`, the App's JWT `appJwt()` RS256 with the client ID as issuer, `pkcs8()` wrapping GitHub's PKCS#1 key; the token asked for the reports repository and `issues: write` only, kept until 5 min before it ends; a 401 drops it once) and the issue, titled by `issueTitle()`, its body `issueParts()` (`quiet()`: `@` + zero-width space, so no one is notified; the contact first; `CHUNK` 60,000 characters each, the rest as comments, at most `MAX_PARTS` 4, then cut); no labels. Answers `{ok, number}` or `{ok: false, error}` (400, 403, 405, 413, 429, 502 with no detail). `relay/README.md` has the setup (the private repository, the App, `wrangler deploy` and secrets, a curl test) and how to read the queue (`gh issue list -R Dude4Linux/arkivet2fs-reports`).
- Load as unpacked extension in Chrome/Brave via `chrome://extensions` → "Load unpacked" → select repo directory
- After code changes, click the reload button on the extension card in `chrome://extensions`
- Debug with the browser DevTools: service worker console (click "Inspect views: service worker" on the extension card) and page console for content script logs
- **Versions**: `manifest.json`'s `version` is the only place the version is kept, as MAJOR.MINOR.PATCH: PATCH for fixes, MINOR for new features (record kinds, pages, languages, ...), MAJOR for changes that break what users have (stored drafts or persons, the source format). Bump it in the commit that makes the change; a commit that only touches docs or tests keeps it. background.js shows it in the toolbar icon's tooltip (`chrome.action.setTitle()`, "DigitalArkivet to FamilySearch v. 1.1.0"), and the pages' headers show it (`addVersionLink()`); it's also on the extension's card in `chrome://extensions`. Each release is tagged `vX.Y.Z` (annotated, pushed with the commit). 1.0.0 is the version through commit dac6e9b; 1.1.0 adds the languages; 1.1.1 fixes them; 1.1.2 tightens the security checks, adds the GPL, scores birth years and dates against FS's, and lightens the icons; 1.1.3 adds the test harness on sanitized DA pages, removes real family names from the docs and comments, and fixes a census couple and a year-from-age score; 1.2.0 adds the update checker (releases.js, update.html); 1.2.1 searches patronymics under their other spellings (Johan* for Johansdr); 1.3.0 reviews an entry found in both of a parish's church books together (one hit, two sources); 1.3.1 reads abbreviated patronymics (-dat., -datt., -d:r) and compares names with Norphone's rules and Jaro-Winkler; 1.3.2 pairs a baptism's child with the FS child of that first given name and sex; 1.4.0 checks the SourceBox for the source and who has it, updates a source already there, attaches a partly attached source to the rest, compares the record's facts with the tree's in each row, creates new tree persons from the linker, closes the FS work tab when done, and pairs a marriage's fathers and in-laws; 1.4.1 matches more old spellings of names, asks for the www. hosts only, pauses requests while DA is down or refusing, and gives a new person FS's standard places; 1.5.0 adds the record's facts to the tree persons (tagged with the source) and compares a source already in the SourceBox field by field; 1.6.0 runs in Firefox too (one package), asks for withheld sites, and makes the update check's GitHub hosts optional; 1.7.0 sends problem reports to a private queue (the report relay); 1.8.0 makes one package, `arkivet2fs-X.Y.Z.zip`, for the stores and the unpacked install.
- **Releases** (`release-plan.md`, Phase 2): the package is the source files, zipped. `tools/build.mjs` builds from a git ref, never the working tree: `git ls-tree` of the commit, every path either shipped (`SHIP`: manifest, `_locales`, the root's `.js`/`.html`/`.css`, the PNG icons and `icon32.svg`, LICENSE, README.md) or excluded (`EXCLUDE`: tests, tools, keys, `docs/`, `relay/`, `.github`, the developer docs, package files, the SVG sources and the banner), else the build stops; `checkReferences()` stops it too when a shipped file is named by nothing (the manifest, HTML `src`/`href`, quoted paths in scripts) or a page or the manifest names an unshipped file. `makeZip()` stores the files uncompressed, in name order, with the commit's time, so a ref always gives the same bytes; `buildAll()` gives the one package, `buildPackage()`'s `arkivet2fs-X.Y.Z.zip` of the shipped files (`shippedFiles()`) with `manifest.json` at the root (since 1.8.0: the stores' upload, AMO refusing a manifest in a folder, and the unpacked install, unzipped into a folder named `arkivet2fs`, the README's `unzip -o … -d ~/arkivet2fs`; update.js downloads it; ci.yml lints it; up to 1.7.0 it was `-chromium.zip` under `arkivet2fs/`, which 1.7.0's update check looks for, so copies of 1.7.0 and older are updated by hand), signed, attested and attached to the release. `--tag vX.Y.Z` checks the tag (annotated, the manifest's version); `--notes vX.Y.Z` prints that version's section of HEAD's `CHANGELOG.md` (write it for users; every version needs one, `tools.test.js` checks the manifest's). `.github/workflows/release.yml`, on a pushed `v*` tag or run by hand for an existing tag: tests (`npm ci --ignore-scripts`: no package's install script runs where the job can write the release and sign attestations), builds from the tag, attests the zip (`actions/attest-build-provenance`) and creates a draft release with the notes. Then the maintainer runs, in a terminal, `cd ~/DevOps/arkivet2fs` and `sh tools/release vX.Y.Z` (no version: v + the manifest's), which takes the draft through four steps, skipping those done: 1. sign (`node tools/sign.mjs vX.Y.Z`, it asks for the passphrase; skipped when the draft has `SHA256SUMS.sig`), 2. test (download the draft into a `mktemp -d` folder with `gh`, `verify.sh` on each zip, `gh attestation verify`, unzip the package into an `arkivet2fs` folder there and ask whether it loaded in Chrome and Brave), 3. publish (asks, `gh release edit --draft=false`, then checks the public files with curl as a user gets them), 4. the stores (`stores()`, only in a terminal and with `~/.config/arkivet2fs/stores.json`, `ARKIVET2FS_STORES` for another: for each store set up there that `node tools/stores.mjs has <store> vX.Y.Z` says lacks the version, it asks, then `stores.mjs upload` sends the zip just checked as published); the folder is removed at the end. On a published release (or without `gh` signed in, when only a published one is seen) it only checks it, then step 4 (silent when no store is set up), with `--keep DIR` to keep the checked zips; `ARKIVET2FS_RELEASES` points it at a `file://` folder in the tests. `sign.mjs` downloads the draft's zip, rebuilds the tag locally and signs only if they're identical: Ed25519 (Node's `crypto.sign`), `<zip>.sig` (base64), `SHA256SUMS` of the zips and sigs, `SHA256SUMS.sig`, uploaded to the draft; the key must match `keys/release.pub` (the tag's, else HEAD's). The private key is `~/.config/arkivet2fs/release-key.pem` (encrypted, made by `sign.mjs --new-key`), never in the repo or on GitHub. Publishing is always the maintainer's answer, never automatic, and so is each store's submission. `tools/stores.mjs` (no dependencies; `main(argv, deps)` with `fetch`, `now`, `nonce`, `sleep`, `log`, `notes`, `env` given, so tools.test.js runs it against fake stores): `storeConfig()` reads stores.json (`chrome`: `publisher`, `item`, `serviceAccount`, the service account's JSON key beside it; `firefox`: `issuer`, `secret`, `addon`), refusing a file others can read (`readSecretFile()`), a store left out isn't set up (exit 3); `zipVersion()` must be the tag's. Chrome Web Store API V2: `googleAssertion()` (RS256 JWT, scope `chromewebstore`, an hour) exchanged at `oauth2.googleapis.com/token`, `:upload` (the zip as the body), `:fetchStatus` polled while `IN_PROGRESS` (5 min), `:publish` with `DEFAULT_PUBLISH` (live once approved), warnings logged; `chromeHas()` reads the submitted and published revisions' `crxVersion` (this or newer, not rejected or cancelled). AMO API v5: `amoToken()` (HS256, `iss` the key, a `jti` and a minute, new per request) as `Authorization: JWT …`, `addons/upload/` (multipart `upload`, `channel=listed`), polled until `processed` (10 min), `valid` (else `validationErrors()`), then `addons/addon/<guid>/versions/` with `{upload, release_notes: {'en-US': …}}` (HEAD's CHANGELOG section, `storeNotes()` without `**` and backticks; the license is the previous version's); `firefoxHas()` is that version's detail (404: not). Errors carry the service's message (`answer()`); no token or key is printed. `tools/verify.sh` checks a download with OpenSSL 3 (the package's `.sig`, and `SHA256SUMS` when it's next to it; without `gh`, `release` downloads the zips `SHA256SUMS` lists with curl); `tools/release` has no `.sh`, so ci.yml names it for `sh -n` and shellcheck; the README gives the key's fingerprint. `dist/` is gitignored.

## Host Permissions

The extension requires access to `https://www.familysearch.org/*` and `https://www.digitalarkivet.no/*` (those hosts only, since 1.4.1; the host checks `isDigitalArkivet()`, `onDigitalArkivet()`, `fetchResultPage()` and `onFamilySearch()` accept the same, and `onDigitalArkivet()` (da_record.js) is DA's for the record readers), for the farm check (farms.js) `https://www.dokpro.uio.no/*` (Rygh) and `https://ws.geonorge.no/*` (Kartverket), and, as `optional_host_permissions` asked for on the Updates page (since 1.6.0), for the update check `https://api.github.com/*` and `https://release-assets.githubusercontent.com/*` (where GitHub's asset downloads redirect; it sends no CORS headers).
