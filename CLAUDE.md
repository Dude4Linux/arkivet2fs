# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**arkivet2fs** is a Chrome/Brave browser extension (Manifest V3) that extracts genealogical record data from Norway's DigitalArkivet (digitalarkivet.no), turns it into a FamilySearch.org source, and attaches the source to the tree persons the record names.

### Workflow

1. On an FS person page, the "Digital Arkivet" entry (fs_person.js) opens the search page (search.html), which searches DA and ranks the hits
2. "Review & Attach" on a hit, or the extension icon on a DA record page (`background.js` injects `da_record.js` and runs its `gatherData()`), opens the linker (linker.html)
3. The user reviews and edits the source and pairs the record's people with tree persons; nothing goes to FS before "Create source and attach"
4. The linker drives an FS tab with `fs_attach.js`: create the source in the SourceBox, attach it to each person by PID, add the tags

## Architecture

- **manifest.json** — Manifest V3 config. No popup; the extension icon click triggers `chrome.action.onClicked` directly. `storage` holds the linker's draft records (session) and FS persons (local).
- **icons/** — the "Kirkebok" mark: an open church book with a pedigree (the person in copper, two parents) growing from its spine; navy `#1d3f5e`, parchment `#f4ecdc`, copper `#d0843f`. `icon128.svg` is the full mark, `icon48.svg` drops the pages' ruled lines, `icon32.svg` has heavier lines (favicon and header of search.html, toolbar at 2x), `icon16.svg` is drawn for 16 px. The PNGs (manifest icons, notifications use `icon128.png`) are rendered from the SVGs with headless Chrome (`--default-background-color=00000000` keeps the corners transparent); `banner.html` → `banner.png` (2x, the README banner; its command is in the file). The FS entry (fs_person.js) shows `icon32.svg` at 24 px, the manifest's only web-accessible resource.
- **background.js** — Service worker:
  - **Click handler**: Validates DA URL, injects `da_record.js` (`files`), then runs `gatherData()` (`func`; both run in the extension's isolated world of the page, so the second sees the first's functions), checks for errors, keeps the result in `chrome.storage.session` (`draft:<time>`) and opens `linker.html?draft=<key>` next to the DA tab.
  - **`rememberPerson()`**: on `searchDA`, keeps the FS person (fs_person.js's `gatherPerson()`, with the family's PIDs) in `chrome.storage.local` as `person:<PID>`, and `persons` (`{pid, name}`, most recent first, at most `MAX_PERSONS` = 30; older `person:` keys are removed), for the linker.
  - **`onInstalled` listener**: injects `fs_person.js` again into open FamilySearch tabs after an install, update or reload (failures, e.g. discarded tabs, are only logged).
  - **`showErrorMessage()`**: Chrome notification-based error display.
- **da_record.js** — reading a DA record page, used by background.js (injected into the DA page) and by search.html (da_verify.js, on fetched record pages). It uses no other file and declares only functions at the top level, since it's injected again on every click and a second top-level `const` would throw. `extractRecord(document, pageUrl)` does all the extraction (the parameter shadows the global `document`; `pageUrl` stands in for `location`, so it works on `DOMParser` documents) and returns the citation, notes, title, people, and `fields` (the open person's own fields, labels lowercased: `destination`, `marital status`, `migrating to`, ...). `gatherData()` runs it on the open page. If the open page belongs to someone other than the record's principal (e.g. the father on a baptism), `gatherData()` fetches the principal's own page (`/en/<permanent ID>`), parses it with `DOMParser`, and extracts from that instead, so citation, notes, title and link all describe the principal. If that fails, it falls back to the open page. Use `textContent`, not `innerText`, because fetched documents aren't rendered. Helpers inside `extractRecord()`:
    - `validatePermanentId()` — validates 2-alpha + 14-digit format
    - `parseRecordType()` — maps ID prefix to record type (`pd`→birth, `pv`→marriage, `pk`→confirmation, `pg`→death, `pa`→probate, `pf`→census, `pe`→emigration, `pu`→out-migration, `pi`→in-migration, etc.)
    - `formatDate()` — handles full, partial, and missing dates
    - `translateRole()` — Norwegian→English role translation (barn→Child, konfirmant→Confirmand, far→Father, utflyttar→Out-migrant, etc.)
    - `readFields()` / `fieldMap()` — read DA's `<div>Label:</div><div class="ssp-semibold">Value</div>` pairs from the DOM (all field parsing goes through these)
    - `FIELD_CODES` / `translateCensusPosition()` / `translateFieldValue()` — English for coded values, per field: census family position, marital and residential status (HISTFORM codes from DA's key, https://www.digitalarkivet.no/en/content/abbreviations-census; e.g. hp→Head of Household, tj→Servant, fl/l→Lodger, b→Visitor; marital status also as written out: Ugift, Gift, Enke, Enkemand), gender, legitimacy (e/u), roles, and ages ("57 a", "27 A."→"57 years", "27 years")
    - `expandAbbreviations(text, more)` — adds English after abbreviations (`ABBREVIATIONS`, case as written) and whole occupation/position words (`OCCUPATIONS`, any case, old and new spellings) in church-book positions and census occupations, keeping the transcribed text: "Gmd."→"Gmd. [farmer]", "Hj. Søn"→"Hj. Søn [son living at home]", "Murer"→"Murer [mason]", "Pladsfolk under X"→"Pladsfolk [crofters] under X". Census family positions written out instead of coded (1801: "Hosbonde", "Hans kone") also get `RELATIVES` ("Hans kone [wife]"), which occupations don't, since they use family words in passing
    - `extractChurchPeople()` — extracts persons from `#collapse-section-0` `.data-item`s (birth/marriage/death/probate records); the open person (`.data-item.current`) is always included and marked primary
    - `extractCensusPeople()` — extracts residents from `#collapse-persons` `.data-item`s (census records); this lists everyone at the residence. DA shows them as cards (`h4 a`, label/value fields; fetched pages) or, with the table view the user's browser has, as `tr.data-item` rows: `rowFields()` maps the cells by the `th` headings, taken from floatThead's floating copy of the table when the table's own `th`s are empty (the open page)
    - `censusHouseholds()` / `censusHousehold()` — split the residents into households and pick the open person's. A residence can hold several (a family, lodgers, the old parents on føderaad, ...); each starts at a resident with "H.no." set (not always the "hp"), or at each "hp" when none has an H.no. In the 1801 and 1865 censuses every resident has an H.no. (01, 01, 02, ...), so there a household starts where the number changes (lodger households elsewhere each have "1", so this rule is used only when all residents have one). A household's first resident with no family position (1865) is its "Head of Household". The other households are returned as `others` and listed in the notes under "Also at the residence, household no. NN"
    - `extractSourceInfo()` — extracts parish, county, source title from page title and detail sections
    - `extractScans()` — scanned-image link(s) from the `#scannedImageLink` toolbar button (`data-scans` holds image permanent IDs: `kb` church book, `ft` census); empty when the record has no scan
    - `buildCitation()` — Evidence Explained–style citation (see `citation.md`): place general→specific (Norway, county, parish/district/municipality from the source title, church), quoted source title, record section, census district/residence/household, protocol/page/line/entry (an emigrant protocol's page and line come from `#collapse-more-info`, read only for emigration since probate pages have it too), entry description (`describeEntry()`), date; then "database, National Archives of Norway, Digitalarkivet, Permanent ID <id> (<permanent link> : accessed <today>)" and "scanned image <id> (<link>)"
    - `recordPrincipal()` — who a record is about, whichever person's page is open: the child (baptism), couple (marriage; the groom's page is used), deceased (burial), confirmand (confirmation), head (first person) of the census household, the emigrant or mover (emigration and moving records; an emigrant protocol lists the travel group, who aren't family, so only the open person counts; a moving record's role is in the person's own fields, "Role: utflyttar"); used by `describeEntry()`, the title, and the switch to the principal's page
    - FS title is "<year>, <principal> - <source title> - <record type>"; a baptized child without a known surname gets ", child of <father/mother>" ("son"/"daughter" when the child's own page gives the gender), since surnames aren't guessed, and a census gets "<head> household, <residence>, <census district>" ("1865, Halvor Larsen household, Bakken nedre, Nordlien - Vågå - Census"; the names from the `div.parent-post > h4` lines "Census district: 005 Nordlien", "Rural residence: 0008 Bakken nedre" without their numbers, none when DA gives only a number such as "001*"; also returned as `census: {district, residence}`) (Birth, Marriage, Burial, ...), FamilySearch's year-first style; "Church book from" / "<year> census for" are dropped from the source title, DA name variants (`%...%`) are stripped from the name, and the type is omitted when the source title already names it (probate)
    - `buildNotes()` — permanent ID, a census's district and residence lines as DA writes them, the open person's own fields (DA's "Last name" holds everything after the first given name; `noteNames()` keeps only its last word as the surname, with a farm-part word such as Nedre/Øvre, and moves the rest to the given name: "Hans" + "Sørensen Lindemann" → "Hans Sørensen" + "Lindemann";split dates like "Date of death: 04-12" + "Year of death: 1854" are merged, and a baptism's date of birth (a burial's date of death) with no year field, "Date of birth: 04-02", gets the record's year, or the year before when the day comes after the record's ("2 April 1821"); full dates like "1812-10-11" become "11 October 1812"), record details not in the citation (banns, remarks, ...), and all persons with their roles (`personLine()`: a census age as "age 35", a year as "b. 1841"), then a census residence's other households
- **fs_person.js** — Phase 1 (see `plan.md`), declared in the manifest for all of `www.familysearch.org` because FS is a single-page app. On a person details page (`/tree/person/details/<PID>`) a `MutationObserver` keeps a "Digital Arkivet" entry (`data-testid=search-digitalarkivet`, icon `icons/icon32.svg`, a web-accessible resource) after Google's in the Search Records panel. The entry is a `cloneNode` of Google's `li`, which keeps FS styling but none of React's handlers. Clicking it runs `gatherPerson()`, which reads FS's `data-testid`s (`conclusionDisplay:NAME|ALTERNATE_NAME|GENDER|BIRTH|CHRISTENING|DEATH|BURIAL|RESIDENCE`; family cards: own families where the person is in `couple-persons`, otherwise the parents), and sends `{action: 'searchDA', person}` to `background.js`. Reloading the extension cuts off the copy running in open FS tabs (`chrome.runtime.id` is gone and `getURL()` throws "Extension context invalidated"), so `extensionAlive()` is checked first and `shutDown()` stops the observer and removes that copy's own entry (`ownItem`). background.js injects the script again into open FS tabs on `chrome.runtime.onInstalled` (install, update, reload; Chrome doesn't inject the manifest's content scripts into open tabs), and a starting copy replaces any entry already there, so the entry comes back without reloading the page. It also answers `{action: 'readPerson'}` (linker.js, on a details page it opened) with `{person: gatherPerson()}` once FS shows the name and family cards (`readWhenShown()`, 20 s), or `{error}`.
- **background.js `personToQuery()`** — turns that person into search criteria in the address of `search.html`, named like FS's record search (`q.givenName`, `q.surname.1`, `q.birthLikeDate.from/to` ±2 years, `q.marriageLike…`, `q.residence…`, `q.deathLike…`, `q.father…`, `q.mother…`, `q.spouse…`, `q.child…`, `q.farm`, `treeref`), and opens the page next to the FS tab. `splitName()` follows the patronymic convention: the given names run up to the patronymic (-sen/-søn/-son, -datter/-dotter, -dtr., -sd.), the patronymic is the surname, and words after it (`rest`) are checked with `farmNear()`; with no patronymic, the last word is the surname. `personToQuery()` is async: the message handler waits for it before opening the tab.
- **farms.js** — loaded with da_places.js by `importScripts` at the top of background.js. `farmNear(name, places, anywhere)` tells a farm from a family or place-derived name (Lindeman): a farm of that name must lie in a municipality or county of the person's FS places (any farm with `anywhere` and no places). It asks Rygh's *Norske Gaardnavne* (`dokpro.uio.no`, UTF-8 `GNAVN`, an HTML table of farm, parish, historical municipality and amt; `parseRygh()`, `amtCodes()` with `PLACE_ALIASES`), then Kartverket's place names (`ws.geonorge.no/stedsnavn`, Gard/Bruk, modern counties via `MODERN_COUNTIES`), with a 5 s timeout each and a cache by name, and also tries the name without Nedre/Øvre/Søndre/... A confirmed farm becomes `q.farm`; otherwise the rest is the surname and the patronymic another name. A last name without a patronymic is also a farm when one lies in the person's places. Uses a local `foldFarm()`, since a `const` of da_places.js isn't visible to the Node tests that `eval` the files separately.
- **search.html / search.js / search.css** — Phase 2 search page (an extension page; no inline scripts). The address is the only store of criteria: the FS-style sidebar (`GROUPS`, on the right with results on the left, as on FS) is filled from it, and Search writes the edited criteria back with `pushState`, so Back/Forward work. Relatives have a use checkbox (`q.fatherSkip=1`, `q.childSkip.1=1`; `profile()` ignores them), "Where to search" adds DA counties/municipalities as chips (`m=`, `c=`; every query gets them as `m[]`/`c[]`, which DA ORs, instead of the automatic narrowing; FS places' municipalities are suggested, never pre-selected), and "Record kinds" (`KINDS`, `off=`) turns queries off by `query.kind` (the id up to `-`). Checkboxes and chips submit at once (`requestSubmit`); unchanged searches come from the page cache. The page copies the look of FS's record search (search.css: Noto Sans 16 px, teal `#057091` buttons and `#005c82` links, FS's grey event boxes in the criteria panel, whose Search button sticks to its bottom under a sticky header); each hit is a row in FS's columns (`hitRow()`: name, role and source link; events, with DA's dates as FS writes them via `displayDate()`, "6 April 1845"; how it matches; score) under column headings (`colHead()`). `hintFor()` tells what is still missing (the query's goal), or what to change when every search found too many hits or none. search.js reads the place tables only through da_places.js functions (`municipalityCodeList()`, `countyName()`, ...), since the jsdom tests can't see another file's `const`s. Results: `renderResults()` lists the queries (each with "N hits from K of M searches" and an "Open on DA" link to the first search that was read; `stepList()` lists every search run, its step and place, linked to DA, with its count), runs them one at a time (a newer search cancels an older one), and after each one re-renders the merged, scored hits by group (merged per step, so the step's `reasons` count); hits scoring below 0 are dimmed. Each group shows `PAGE_SIZE` (10) hits, with a pager below when it has more (`groupSection()`); the page of each group is kept in `groupPages` while hits come in and are re-ranked, and cleared by a new search. Then `checkHits()` reads the record pages of the best hits (da_verify.js; at most `MAX_CHECKS` = 40, each time the best unchecked one, re-rendering after each), stores the reasons on the hit as `checks` (or `checkError`), and says so under the hit ("record checked", "record not read: …") and in `.check-status`; it stops when DA refuses requests and is skipped when a search was refused. Scripts load in this order: da_places.js, da_search.js, da_match.js, da_record.js, da_verify.js, search.js (linker.html the same, with linker.js last).
- **da_places.js** — DA's counties (`DA_COUNTIES`, `c[]`) and historical municipalities (`DA_MUNICIPALITIES`, `m[]`; a code starts with its county's, Oslo 03 and Bergen 13 are their own), generated from DA's advanced-search form (November 2026); `PLACE_ALIASES` (old and new names: Oslo = Christiania/Chra., Vest-Agder = Lister og Mandal, town abbreviations such as Fr.stad/Fstad, Fr.hald, Chr.sand, Chr.sund, ...); `municipalityCodes(place)` turns an FS place into the municipality codes its parts name (aliases included; a name several counties share is narrowed by the FS county; Oslo adds Aker via `MUNICIPALITY_NEIGHBOURS`); `countyCodes(place)` the county codes of the counties it names and of its municipalities. Loaded first. Helpers shared between these scripts are `function` declarations, not `const`s, so the jsdom tests (which `eval` each file) see them.
- **da_search.js** — DA advanced-search queries (`/en/search/persons/advanced`), loaded by search.html after da_places.js, before da_match.js and search.js. `profile(criteria)` turns the sidebar's criteria into one person (year ranges, spouses, children, places, farms). `buildQueries()` gives one query per life event, each a series of searches from strict to relaxed: `steps` (the names: `pairSteps()` gives the person and a relative with both full names, then one name left out at a time, the mother's or bride's surname first since records often leave it out, then both by given name only; `alone()` the person by name; each step has the `reasons` all its hits match, "mother Ing* Lars* for Ingrid Larsdr"), `levels` (where: `levelsFor()` gives the municipalities (`m[]`) of the event's FS places, then their counties (`c[]`, `countyCodes()`), then Norway as a fallback; or only the places chosen under Where to search) and `goal(hits)` (what's still missing: by default any record; for children's baptisms a baptism in each known child's year (or the next), for the census each of `FULL_CENSUSES` in the lifetime; shown as "Not found: …"). `searchPlan()` orders them: the "named" steps (a surname of the person or a relative, or a farm) at each local level, parish before county; then, while nothing is found, the named steps in all of Norway and the other names (`variants`, fallback steps) in the widest local level; last the given-name-only steps in the narrowest place only (in the county they'd bury the person's records, and meet the goal with other people's before the named steps had widened). `runQuery()` runs the plan until the goal is met; a search with more hits than `readLimit()` (`MAX_PAGES` × 50 = 100) isn't read (most would be other people) and that step isn't run wider; it returns `{found: [{step, hits}], searches: [{step, place, total, read, params}], missing}`. The queries: own baptism (`roles[]=barn`, first given name with the father's or mother's full name as related person, then two given-name stems alone (all must match: Ann* Magdalin*), then a parent's given name only, then the first given name alone; DA's transcriptions of parents can be far off: Anna Lindeman's Johannes and Gjertrud are "Johanne Olsen" and "Johanne Stubbe"; skipped with a hint when no parent or birth year is known), confirmation, marriage (one per spouse, the spouse as related person, then the person alone), children's baptisms (the person as `far`/`mor`, one query per FS spouse with the spouse as the other parent, `related_roles[]=mor`/`far`: Lars Halvors* + mother Ing* Lars* in Vågå finds five of six children, the person's name alone thousands of fathers; with no spouse, or the spouse unticked, the person alone), census (`jt[]` census years in the lifetime, `birth_year` ±3), emigration (`sc[]=em`: emigrant protocols, passenger lists, passports; from birth, `birth_year` ±3), moving away (church books' moving lists, `lt[]=uf`/`fl`, records `pu`/`pi`; no `birth_year`, since many give no age), burial (skipped when FS has the death outside Norway), children's marriages (`childmarriage`: `roles[]=brudgommensfar`/`brudensfar`, since church books name the couple's fathers only; from the eldest FS child's 16th year to 45 years after the youngest's birth; skipped for women), and all records under the name. When FS has no birth, `estimatedBirth()` (`P.estBirth`) derives one from the marriage (at 16–50) and children (a father at 18–65, a mother at 18–50) for the lifetime and the census, emigration, confirmation and marriage years ("born about"); scoring never uses it. Relatives' given names go to `related_first_name` through `relatedStem()`: the shared start of the name's forms in `GIVEN_NAME_FORMS` (Ingeborg/Ingebjørg/Ingbjør → Ing*; DA's own variants don't link them), otherwise `givenStem()`. Name rules learnt from DA: each word of `firstname` must match one of the given names, so the other queries use the first given name only; a trailing `*` works (DA still applies its variants to the stem: Christ* finds Kristian), a `*` inside a word or `?` doesn't. `givenStem()` cuts a final vowel (Anna → Ann*, finding Anne; Magdaline → Magdalin*; Jon, Ole, Johannes stay as they are), `surnameStem()` gives Aslaksen → Aslaks*, Tollefsdatter → Tollefs*, Lindeman → Lindem*; `patronymicOf()` derives the patronymic from the father (Aslak → Aslaksen, Johannes → Johannesdatter, Ole → Olsen), used as the surname when FS has none and for scoring; parents' patronymics aren't used as `related_last_name`. The other names (`variants`, at most three: the father's patronymic, FS alternate names, `PATRONYMIC_SPELLINGS` such as Johans*/Johannes*) are fallback copies of the first step with the person's full name. Farms (`q.farm`) get a "Records at <farm>" query (`domicile`). Never filter on `genders[]`: DA drops records without a gender (many censuses). `parseResults()` reads `#searchResultList .unit`s with `DOMParser`; `fetchResultPage(url, store = true)` spaces requests 1 s apart, caches pages in `sessionStorage` (not with `store` false: da_verify.js keeps only the extract of a record page), and reports 403/429 as DA refusing requests; `readLimit()` is a function so the jsdom tests of search.js see it.
- **da_match.js** — `mergeHits()` keeps each record once (by permanent ID) with every step that found it; `scoreHit()` scores it against the profile with visible reasons (✓ match, ≈ close or a DA name variant, ✗ contradiction): given names (`nameMatch()`: the same, one of its forms (`nameForms()`, da_search.js: Ingbjør = Ingeborg, Marit = Margit, Knut = Knud; `GIVEN_NAME_DIALECT` adds dialect spellings such as Imbjør/Imbjor to a group without making them search stems), the stem, or the same consonants via `skeleton()`, so Anne ≈ Anna, Magdalen = Magdaline, John = Joen = Jon, an h next to a consonant is dropped: Ragnihld = Ragnhild = Ragnild, and an old final j after a consonant is i: Sirj = Siri = Siry) and surname stem (or a patronymic from a spelling of the same father's name, `patronymicBase()`: Halvardsen ≈ Halvorsen), sex (only a mismatch counts), birth year (+4 for FS's own year, the middle of the ±2 range), event year by role (baptised/married/buried), before birth or after death, too young for the role (`MIN_AGE`, which flags namesakes; a couple's father at least 34), a known child's birth year, FS place parts or their old names (`PLACE_ALIASES`) in the hit, farms (also spelled with the same consonants: Hægbostad = Hægebostad), the steps' own reasons (once per relative, from the strictest step that found the hit: "mother Ing* Lars*", not also "mother Ing*"), and what the record page said (`hit.checks`, from da_verify.js). `hasWord()` is a function declaration because da_verify.js uses it. On baptisms and confirmations, which give all given names, each one FS doesn't have is -1. `groupHits()` groups by record kind and role (`GROUP_ORDER`; out- and in-migration go to Moving; a father's row in a baptism goes to Children's baptisms, a groom's or bride's father's in a marriage to Children's marriages, a godparent's to Other), best first, and hits with the same score by event date, earliest first (`dateKey()`; undated last), so a couple's children come in order.
- **da_verify.js** — checks close hits on their record pages, since a hit gives only one person's name, years and residence (three Peer Aslaksens in the 1801 census score alike). `hitsToCheck()` takes the best few of each group (`CHECK_PER_GROUP`, 12 children's baptisms, 6 children's marriages, otherwise `CHECK_DEFAULT` 3; score ≥ `CHECK_MIN_SCORE`; groups in `CHECKED_GROUPS`); in children's baptisms `childYearHits()` comes first: the best three hits of each known child's years, for children no checked record names yet, since a namesake's records can outscore the one baptism that has the father under another spelling. `fetchRecord()` reads the page with `extractRecord()` and keeps `{people, others, fields, recordTypeInfo, recordDate}` in `sessionStorage` (`rec:<url>`). `relativesInRecord()` finds who'd be the person's father, mother, spouse and children by both roles (`roleKind()`, `ROLE_KINDS`: DA roles and census positions, including 1801's free text such as "Hosbonde", "Hans kone", "Deres børn"; only the first of "d, fl" counts); in a census household the head and the head's spouse are both a child's parent candidates; a groom's or bride's father (`groomFather`, `brideFather`) has the groom or bride as child. `checkRecord(record, profile)` gives reasons like `scoreHit()`'s: an FS parent or spouse named in the record ✓ +3, another name there ✗ -2 (not for census parents: foster and step-parents), an FS parent heading (or married to the head of) another household at the census residence ✓ +2 ("father Halvor Halvorsen at the same residence"), FS children ✓ +2 each (at most three, birth year ±2, from an age in a census or a baptism's year), a baptism naming another child than the FS child born that year ✗ -2 (it cancels the hit's year match), unmarried in a census after FS's marriage ✗ -3, an emigrant's destination among the FS places ✓ +2 ("going to Denver Col."). DA's transcriptions of names can be far off, hence the small minus.
- **linker.html / linker.js / linker.css** — Phase 3, the DA Linker (an extension page, styled on search.css's variables): the pause before anything is saved on FS. Opened as `linker.html?rec=<DA record page>&pid=<PID>` (the search page's "Review & Attach" in `hitRow()`; the hit's person, the open person of `rec`, is the FS person) or `?draft=<key>` (the toolbar icon). `loadFromDA()` reads `rec` (`fetchResultPage(url, false)`, `extractRecord()`) and for the source fields the principal's page (`principalUrl`), falling back to the open page; `gatherData()` adds `openPerson` for the draft. `recordPeople()` gives the rows (the record's people, plus the open person when the principal's page leaves them out, e.g. a godparent) with `current` on the anchor; in a census also the residence's other households (`record.others`, `household` 1, 2, ...), listed under a heading per household (`householdHeading()`). The FS family is `chrome.storage.local` `person:<PID>` (`treeFamily()`: the person, father, mother, spouses, children, each with a PID); from the icon, the last person searched (`persons[0]`) is used when `findSelf()` finds their given name in the record. `suggestPairs()` pairs the FS person's entry, then by `relativesInRecord()` from that entry the relatives with an FS relative's given name (`hasGivenName()`, `givenOf()`; children also by birth year ±2); a single church-book parent or spouse with another name is only named in the hint, and in a census only names count. A census instead uses `suggestResidencePairs()`: the FS person is the anchor (trusted) or the resident with their given name and birth year ±3 around whom most of their family lives (Lars Halvorsen 75, not his grandson Ole 15); from there it pairs outward through the tree (`treeRelatives()`: father, mother, spouses, children), from each paired resident to their tree relatives anywhere at the residence (`residentFit()`: the given name or a form of it, or a close one, Mari for Marit, only with a fitting year, household role and a sex both tell (`recordSex()`: patronymic or family position, since census rows have no gender); FS birth year ±3; in the paired resident's own household the relation must fit (`householdRelatives()`, where a household's first resident without a family position is its head: 1865's "hans Fader"); otherwise ages must fit: a parent 15 years older, a child 15 younger, a spouse within 25). The relatives' own families come from FS: `readResidence()` reads, while residents are unpaired, the families of paired relatives in households with unpaired residents (else the two eldest; `treesToRead()`; at most `MAX_TREE_READS` = 8 in `MAX_TREE_ROUNDS` = 3) with `readTreePersons()`: `person:<PID>` or `tree:<PID>` (`chrome.storage.session`) if kept, else one background tab on `/en/tree/person/details/<PID>` asked `{action: 'readPerson'}` (fs_person.js; the tab is shown for a moment if FS didn't draw it in the background, then closed), and updates the rows in place (`row.update()`, leaving rows the user changed), with the tree pool widened (`treePool()`: "wife of Halvor Larsen") and a status line (`#tree-status`). Each row (`personRow()`): editable name, role, a select of the family plus "Another person (PID)…", tags (`TAGS`, defaults by `defaultTags()`: a baptized child Name, Sex (FS's chip `Gender`), Birth, Christening; a deceased Name, Death, Burial; census Name, Sex, Residence; otherwise Name) and a reason (`defaultReason()`; a census's "at <residence>, <district>" and the household number of another household). `surnameSuggestions()` offers, for a one-word name, the paired FS person's name and for a child the father's patronymic (`patronymicOf()`, by the paired person's sex or the record's gender field, both when unknown). `rename()` carries an edited name into the title and citation (`renamePhrase()`: whole names after "^"/", "/" and "/" of ", before ","/" -"/" and "/" household"/";") and the notes' "Role: Name" line (`renameNoteLine()`), and drops ", son of X" from the title when a baptized child gains a surname (`dropChildOf()`). `run()` checks the plan (`readPlan()`: a title, valid and distinct PIDs), opens the SourceBox in a new active tab (timers in background tabs are throttled), and runs `fs_attach.js` steps (`step()`: inject, `chrome.tabs.sendMessage`, 2 min timeout), logging each in `#log`: `createSource`, `attach` per pair, then `tag` on `/en/tree/person/sources/<PID>` for pairs FS didn't offer tags for.
- **fs_attach.js** — injected by linker.js into an FS tab (again for each step and page; `window.__arkivet2fsAttach` guards the listener); answers `{linker: step, args}` with `{ok, ...}` or `{ok: false, error}`. Values go in through the native `value` setter plus `input`/`change`/`blur`, so React sees them. `createSource`: on `/sources/sourcebox` (else: sign in), uses a row whose title (`row-<ID>-title`) equals the title if there is one (a second run makes no copy); else `source-box-create-source-button`, the fields `source-date-field`, `source-title-field`, `source-web-page-field`, `source-citation-field`, `source-notes-field`, `source-save-button`, and the new row's ID (one not there before). `attach`: `row-<ID>-attach-button` → `find-options-by-id-tab` → `find-options-id-field` → `find-options-by-id-next-button` → `reason-to-attach-reason-field` (checks the PID in `reason-to-attach-person`) → `reason-to-attach-attach-button`; if FS then shows its tag dialog, the tags are set there. `tag`: the source's panel on the Sources tab (a `div`, the nearest ancestor of `source-button_view-<ID>` that holds a `source-heading-section`; the View button is in a hidden menu, there also while the panel is closed; else the panel whose heading has the title), opened by clicking its heading's `button[aria-expanded]` (only an open panel has the tag buttons), `source-add-tags-button-<ID>`, then `setTags()`: clicks the `source-vital-tag-chip-<Name|Gender|Birth|Christening|Death|Burial>` chips asked for that lack `data-selected` (adds only, never removes), a residence via `add-tag-button` → `source-conclusion-tag-chip-RESIDENCE` only when there is exactly one, and `add-tagging-save-button`. FS's context mode (`sourceBox?context`) isn't used: the person isn't in its URL.

### Key Constraints

- `da_record.js` executes in the DA page context (injected via `chrome.scripting.executeScript`) and in search.html. **It must not use anything from other files**, and declares only functions at the top level (it's injected again on every click).
- Form filling in `fs_attach.js` sets values through the native setter and dispatches `input`, `change`, and `blur` events for FamilySearch's React-based UI to register them.
- FS's `/platform/` API isn't used (it needs a session token); attaching is UI automation of the SourceBox and the Sources tab, started only by the user on the linker page.
- DA Permanent IDs: two alpha characters + 14+ numeric digits (e.g., `pd00000012345678`). The prefix indicates record type (see `ai_prompt.md` for the full table).

### DA Page Structure Differences

- **Church records** (birth `pd`, confirmation `pk`, marriage `pv`, death `pg`): URL `/view/NNN/pXXX`, persons in `#collapse-section-0`, record details in `#collapse-section-1`, header in `div.parent-post > h4`
- **Census records** (`pf`): URL `/census/person/pfXXX`, persons in `#collapse-persons`, details in `#collapse-more`, no parent-post header

## Development

This is a browser extension with no build step, no package manager, and no test framework. To develop and test:

- Load as unpacked extension in Chrome/Brave via `chrome://extensions` → "Load unpacked" → select repo directory
- After code changes, click the reload button on the extension card in `chrome://extensions`
- Debug with the browser DevTools: service worker console (click "Inspect views: service worker" on the extension card) and page console for content script logs

## Host Permissions

The extension requires access to `https://*.familysearch.org/*` and `https://*.digitalarkivet.no/*`, and for the farm check (farms.js) `https://www.dokpro.uio.no/*` (Rygh) and `https://ws.geonorge.no/*` (Kartverket).
